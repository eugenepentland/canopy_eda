# Worktrees

> Moved verbatim from CLAUDE.md (2026-08-19); linked from its Reference Docs section.

This repo routinely has several git worktrees in flight under `.claude/worktrees/` (one per feature branch). The directory is `.gitignore`d. These rules are mandatory for every project update:

- **Never edit any project file directly on `main` — always work in a worktree.** This includes compiler/server code, tests, design `.sexp` files, documentation, `SPEC.md`, Guardian/config metadata, and generated files. Before the first write, create a feature branch in its own worktree under `.claude/worktrees/` (`git worktree add .claude/worktrees/<short-name> -b <branch> main`), change into it, confirm its branch/status, and do all edits, generation, builds, tests, acceptance, staging, and commits there. Read-only inspection on `main` is fine. `main` receives completed work only through a reviewed branch merge; do not merge unless the user requested it. Editing `main` directly risks loose state being swept into auto-commits and silently reverting other branches. When an authorized branch is ready to integrate, merge it into `main` (`--no-ff`, "Merge: …"); the local `post-merge` hook handles the rebuild/restart described below.
- **Merging into `main` auto-deploys prod (2026-06-17).** The deploy is **tracked** in `.githooks/` — install it on a fresh clone with `.githooks/install.sh --deploy`, check it with `.githooks/install.sh --check`, and see [.githooks/README.md](.githooks/README.md). Before merging a completed commit, run `.githooks/prepare-release.sh` in its worktree: Guardian runs once, then the full suite and ReleaseSafe build run concurrently in separate local caches and publish an exact-commit candidate only if both pass. The detached post-merge hook validates and installs that candidate, then health-checks the restart; if the merge created a different commit or no candidate was prepared, it performs the same preparation on `main` first. A failed gate, test, build, checksum, or install leaves the running service untouched. Disable with `.githooks/install.sh --uninstall-deploy`; `DEPLOY_DRY_RUN=1` makes the worker log-only. Every merge deploys immediately through a coalescing queue (no hold period; the `Deploy: skip` trailer is retired) — see the deploy bullet below.
- **A bad build can't leave prod down (2026-07-25).** After the restart, `deploy-prod.sh` health-checks the live server (`/healthz` → 200, for up to `HEALTH_TIMEOUT`=90 s). On failure it keeps the bad binary at `.git/deploy-failed-netlisp`, restores `.git/deploy-lastgood-netlisp` and its paired `.git/deploy-lastgood-id` (installed **by rename** — the failed binary is still running, and `cp` over it fails with `ETXTBSY`), and restarts prod on that. `.git/deploy-last-hash` is written **only** on a passing health check, so `wait-deploy.sh` reports a rolled-back deploy as a failure. The systemd unit uses **`Restart=always`, not `on-failure`**: systemd counts `SIGTERM` as a *clean* exit, so `pkill netlisp` / `fuser -k 7050/tcp` used to leave prod dead-and-not-restarted (a 7 h 502 outage on 2026-07-25). The manual deploy (`zig build --seed=1 -Doptimize=safe` in the main checkout + `systemctl --user restart netlisp.service`) is still the path for off-merge builds or when the hook is disabled.
- **Every merge DEPLOYS immediately — there is no hold period (2026-08-14).** No merge builds prod inline: it arms `.git/deploy-pending` at **window 0** and is deployed in the same breath (the arming run execs the worker itself), so an idle box starts building at once; a merge landing while a deploy is building queues instantly on the deploy lock and starts the moment the build finishes; and N merges landing during one build cost at most ONE follow-up deploy of the accumulated head (a queued deploy re-checks after acquiring the lock and no-ops if its head already shipped).
  - **The `Deploy: skip` trailer is RETIRED.** Do not write it on merges; one that still carries it is logged with a note and deploys like any other. There is no deploy-or-defer decision to make or announce any more — merge when the branch is ready, and the queue handles contention. (`DEPLOY_SETTLE_SECONDS>0` in the merging shell restores a timer-deployed settle window if batching ever matters more than immediacy again.)
  - `wait-deploy.sh` waits through a queued deploy and succeeds on **ancestry** (your head may ship inside a newer coalesced head); it exits 2 only for a positive-window hold ending beyond its own deadline — the knob/legacy exception, not the normal path.
  - **A FAILED deploy holds.** The marker was consumed, so nothing retries automatically; the head lands in `.git/deploy-failed-head` and `install.sh --check` reports the HELD state with the retry command (`deploy-debounce.sh --now`, or any later merge). Prod stays on the rolled-back binary meanwhile — a hold is a loud state, not a silent gap.
  - **Re-read these bullets from CURRENT main before you merge** (`git show main:CLAUDE.md`, or read the file in a worktree freshly branched from main). Your copy of CLAUDE.md is a snapshot taken when the session STARTED, and on this repo main moves several times an hour — two generations of this very policy landed mid-session on 2026-08-14, each invisible to every session already running. See [.githooks/README.md](.githooks/README.md) and `scripts/test_deploy_debounce.sh`.
- **Prepare the release in the worktree, on a freshly rebased branch (2026-08-10).** Make `.githooks/prepare-release.sh` the branch's FINAL step, and rebase onto current `main` first. A candidate records the source **tree** it was verified for, and a `--no-ff` merge of an up-to-date branch produces a commit whose tree is byte-identical to that branch tip — so the merge on `main` finds the branch's own verified artifacts, adopts them under the new merge sha, and deploys in **seconds** instead of rebuilding for ~5–6 minutes. Nothing is trusted blind: adoption requires the source candidate's `verified` marker and a passing `sha256sum --check`, and a tree that matches nothing (a stale branch, or any real change on `main` between preparation and merge) simply falls through to the full build.
- **There are no file-type exceptions.** Design files, docs, specs, config, generated references, and Guardian baselines/snapshots follow the same worktree rule as Zig source. Commands that can regenerate them (`zig build docs`, import/export flows, formatters, Guardian acceptance, and similar tools) must also run from the task worktree.
- **Keep the main worktree's tree clean.** If `git status` on main shows anything (uncommitted edits, staged deletions, untracked scratch files), deal with it *before* asking anything to merge branches — uncommitted state on main gets swept into auto-commits and can silently revert work from other branches. Lesson learned the hard way: a partial-revert sitting staged on main deleted the schematic sidebar when another branch was merged.
- **Commit WIP; don't leave it dangling.** Across-session work should land as a `WIP: ...` commit on the feature branch (fine to squash later), never as loose edits in a worktree. Stashes are invisible to automation and to a future you — prefer a commit.
- **Rebase worktree branches onto main weekly or before handoff.** Branches that drift more than a few commits behind main produce wide conflicts and, worse, context-line drift (e.g. a function call surviving a rebase after the function itself was deleted upstream). Small, frequent rebases keep the delta legible.
- **Before bulk-merging worktrees, inventory them.** Run `git status` in each worktree (a `git worktree list` + loop works well). Flag any uncommitted work and decide commit-vs-discard *per worktree* before anything touches main.
- **Retire merged worktrees.** The `post-merge` hook automatically clears the
  just-merged clean worktree's `.zig-cache`; use
  `.githooks/prune-worktree-caches.sh --all --dry-run` and then `--all` to
  reclaim caches from older merged worktrees. This does not delete source or a
  branch. Once no agent or shell still uses one, fully retire it with
  `git worktree remove <path> && git branch -D <branch>`. Fewer live worktrees =
  fewer places for drift to hide.
- **Audit `git stash list` periodically.** Stashes labelled against deleted branches are almost always forgotten work worth reviewing or dropping.
